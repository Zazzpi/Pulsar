# Как объяснить Pulsar на защите

«Я сделал инструмент для продаж поверх существующей WMS. Менеджер наблюдает
за клиентом 90 дней и видит складской контекст. WMS остаётся источником
операционных данных, а мои наблюдения и заметки живут отдельно».

## Технологии: что, где и зачем

| Технология | Где используется и что делает | Почему выбрана | Что сказать проверяющему |
| --- | --- | --- | --- |
| Python | Backend, desktop, скрипты, тесты | Один язык для всего MVP | «Не нужно поддерживать два стека» |
| PyQt6 | Окна, таблицы, вкладки, фоновые задания desktop | Готовые desktop-компоненты и сигналы | «GUI остаётся отзывчивым, пока запрос идёт в рабочем потоке» |
| requests | Desktop обращается к Django по HTTP/JSON | Простой клиент с timeout и проверкой TLS | «Desktop знает API, а не таблицы PostgreSQL» |
| sqlite3 / SQLite | Файл локального кэша на ПК | Входит в Python, не требует сервера | «Это последние просмотренные данные, не основная БД» |
| Django | Авторизация, API, конфигурация, серверная логика | Закрывает потребности MVP одним framework | «Gateway централизует безопасность и нагрузку на WMS» |
| Django ORM | Собственные watches, notes, daily metrics, токены | Удобная работа со своими сущностями | «ORM не меняет таблицы WMS» |
| Django migrations | Версии структуры собственной БД | Воспроизводимый запуск и обновление | «Миграции применяются только к базе Pulsar» |
| Django cache | Повторно отдаёт недавние ответы WMS | Достаточен без отдельного сервиса в MVP | «Один и тот же экран не вызывает SQL при каждом открытии» |
| PostgreSQL WMS | Уже существующий источник складских данных | Это данность проекта | «Читаю через отдельное read-only подключение» |
| PostgreSQL Pulsar | Новые серверные данные приложения | Общие данные доступны с разных ПК | «90-дневное наблюдение не теряется при смене компьютера» |
| Docker Compose | Django и собственная PostgreSQL | Повторяемое локальное окружение | «WMS не запускаю и не изменяю этим Compose» |
| pytest | API, SQL, расчёты, cache, ошибки, Qt smoke | Проверяет поведение, которое легко сломать | «Есть проверки времени наблюдения, изоляции и отказа сети» |
| Git | История проекта; GitHub — удалённый репозиторий | Видно изменения, удобно проверять и откатывать | «Исходники опубликованы в Zazzpi/Pulsar» |

## Два кэша — разные задачи

Серверный кэш экономит запросы к WMS для всех пользователей gateway. Локальный
кэш сохраняет последние данные конкретного пользователя на конкретном ПК и
помогает при отключении сети. Оба могут устареть. Источником истины остаётся
сервер/WMS, а не сохранённый JSON.

При открытии экрана сначала показываю SQLite, затем запрашиваю сервер в фоне.
Обновление UI выполняется через Qt signals. Если сеть недоступна, сохранённые
данные остаются на экране с предупреждением и временем получения.

## Термины своими словами

| Термин | Как объяснить |

| API | Набор согласованных команд, через которые программы общаются |

| snapshot | Сохранённые значения метрик на конкретный момент или день |

## Как я понимаю карту WMS

| Таблица | Смысл и связь |
| --- | --- |
| `public.clients_client` | Клиент; исходный `id` для фильтрации |
| `public.products_product` | Товар; `client_id` указывает владельца |
| `public.stocks_stock` | Текущий остаток; через `product_id` связан с товаром и клиентом |
| `public.movements_movement` | История; также связана с клиентом через товар |
| `public.orders_order` | Заказ; `client_id` — его клиент |
| `public.receivings_receiving` | Приёмка; `client_id` — её клиент |
| `public.shipments_shipment` | Отгрузка; `order_id` ведёт к заказу, а он к клиенту |
| `public.tasks_task` | Задания склада; есть `client_id`, статусы и дедлайн |
| `lk_wms.orders_receivingrequest` | Намерение принять товар, ещё не фактическая приёмка |
| `lk_wms.orders_shipmentrequest` | Намерение отгрузить, ещё не фактический заказ |
| `lk_wms.billing_billingcharge` | Начисления; `contractor_id` равен `clients_client.id` |
| `public.integrations_integration` | Состояние синхронизации клиента с внешней системой |

Между `lk_wms.contractor_id` и клиентом WMS связь логическая: карта не обещает
внешнего ключа. Во всех SQL таблицы указаны вместе со схемой: похожие названия
в разных схемах нельзя путать.

Остаток — это текущее состояние, а движения — история. Не надо восстанавливать
остаток полным суммированием журнала. Доступно = всего минус резерв. У движения
количество положительное, направление хранится в типе. Отрицательные начисления
уже являются сторно: обычная сумма учитывает их правильно.

`cancelled` и `canceled` — разные реальные коды разных таблиц; их нельзя
«исправить» общей нормализацией. `submitted`-заявка требует внимания только если
соответствующий `wms_receiving_id`/`wms_order_id` ещё пуст.

## Архитектурные решения

**Почему без Redis?** Один процесс Django может хранить небольшой cache в памяти.
При нескольких процессах нужен общий cache — тогда добавлю Redis через Django
cache backend. Desktop этого изменения не заметит.

**Почему без FastAPI?** Django уже даёт авторизацию, ORM, миграции, cache и
маршрутизацию. Второй framework в этом MVP не решает отдельной задачи.

**Почему PyQt не подключён к PostgreSQL?** Пароли WMS не должны попадать на ПК.
Gateway контролирует запросы и нагрузку, переиспользует cache и хранит общую
бизнес-логику. Источник данных можно заменить без обновления каждого desktop.

**Почему read-only?** Мониторинг не должен повреждать складские операции.
Поэтому repository содержит только SELECT, соединение read-only, а в production
нужны также реальные SELECT-only права пользователя PostgreSQL. Приложение не
подменяет администрирование прав.

**Почему SQLite — только cache?** Файл одного компьютера не может быть общей
основной базой отдела. Наблюдения, заметки и учётные записи хранятся на сервере.
Сохранённые данные можно читать без сети, но изменения offline не отправляются.

**Что означает 90 дней?** Это срок наблюдения: точное время старта плюс 90 суток.
Отдельно есть окно просмотра истории операций. Daily snapshots записываются
постепенно и не создают прошлую историю остатков задним числом.

**Почему простые правила вместо AI?** Просроченное задание или сбой интеграции
проверяются однозначными условиями. Это объяснимо и не требует модели.
Близкий дедлайн — допущение 24 часа в настройке; устаревший sync — час по карте.

## Что продемонстрировать

1. Запустить Compose, войти в desktop.
2. Найти клиента; показать сводку и «Требует внимания».
3. Создать наблюдение и заметку; показать, что они хранятся сервером.
4. Открыть остатки и историю с пагинацией.
5. Остановить backend; показать сохранённые данные и предупреждение.
6. Запустить backend снова и обновить экран.
7. Показать pytest и SQL: схемы, параметры, фильтры, LIMIT.
8. Объяснить ограничения: production-схема не проверена, FK детализации нет,
   snapshots требуют расписания, для нескольких серверов нужен общий cache.

Не утверждать, что mock доказывает работу production WMS: он проверяет
пользовательский сценарий и контракт. Для реального подключения нужны
SELECT-only учётная запись, TLS, проверка схемы и планов запросов на сервере.
